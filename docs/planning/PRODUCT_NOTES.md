# 后续产品要求

## 2026-09-16 — 用户录入与内部分类

用户明确提出：最终 lore 由用户录入，系统内部按实体、类别、条目组织。当前 Markdown 文件只是第一阶段实验输入，不是最终资料录入形式。

示例结构：

- 雷
  - 生理结构：双心脏、青少年、其他条目
  - 经历：大地震后失忆、其他条目

以上是用户描述的组织方式示例，不自动加入测试库或认定为正式 canon。

这块暂缓实现，当前仍按原计划完成检索、编码检查和性能测量。后续设计录入与分类时应以该要求为起点，再确定分类由用户指定、程序规则还是其他方法辅助。

## 2026-09-16 — CPU/GPU 兼容与用户选择

用户明确要求保留 CPU/GPU 选项，应用不能依赖用户拥有 GPU。

- 保留自动、CPU、GPU 三种选择；默认自动，有可用 CUDA 时使用 GPU，否则使用 CPU。
- 用户可显式选择 CPU；显式选择 GPU 而设备不可用时给出明确提示。
- 后续界面也应保留设备选择与实际运行设备显示。
- 当前 CLI 已支持 --device auto/cpu/cuda，CPU FP32 检索已在 benchmark 中验证。
- 当前依赖锁面向 Windows CUDA 版 PyTorch；面向普通用户发布时仍需整理 CPU-only 安装方式，避免无 GPU 用户下载不必要的大型 CUDA 依赖。

此处只记录要求，不在本次新增安装器或界面。

## 2026-09-16 — 新设定录入预览与确认

用户希望输入新能力、经历或时间线事件时，看到该实体已有的同类条目和拟新增条目。用户已选择：先显示判断、已有条目和拟新增条目，由用户确认保存。

- 示例：输入“雷能控制时间”，预览实体雷、类别能力、资料库中已有能力条目（带来源）、拟新增原文及不确定/一致/矛盾判断。
- 双心脏归生理结构；天使之力只有真实资料明确记录才展示，不由 LLM 编造条目。分类可由系统建议，允许用户修正。
- 经历显示事件及时间；timeline 保留日期/章节、主体与来源，缺失时间明确显示未指定，不自动推断。
- 预览时状态是待确认，只有用户确认且持久化成功才显示“新设定已记录”，然后显示更新后的同类条目。
- 新概念仍按当前证据不足处理，不自动成为 canon。不确定可以由作者确认建立，矛盾需要作者明确处理，不静默覆盖旧条目。
- 已有同类条目应从实体/类别资料库完整读取，Top-5 语义检索只是判断证据，不等于实体条目全集。
- 本步实现候选约束修复并记录交互约定；分类资料库、确认保存与索引同步尚未实现。

### 2026-09-16 实现进度

分类录入预览/确认追加已可通过 entry.py 体验，实体和类别由作者指定；事件时间可附加。存储源 data/entries.json，生成 Markdown 作为检索适配，确认后自动重建索引；sync_entries.py 可恢复同步。未实现自动分类、别名、旧条目编辑删除或时间线排序。实际资料未加入测试的控制时间能力，隔离集成报告记录于 reports/entry_checks.json。

### 2026-09-16 自动分类更新

人物/类别默认交给本地 LLM 识别建议，作者确认保存；手动参数改为纠正/覆盖入口。输入明示的事件时间可复制，不补写日期。代词人物程序保护并要求澄清。分类只使用通用类别和已有类别，作者可显式指定自定义类别；暂不自动拆多个主体和类别。

### 2026-09-17 响应速度与失败提示

已加入连续录入进程内模型复用，避免每条重载。错误状态显示具体原因与未保存，不等同不确定。当前短案例生成仍需数秒，输出较长会更慢；后续界面需体现加载/识别/判断进度，性能优化须保留可比较的质量 baseline。

### 2026-09-17 通用创作体系要求与进度

用户明确：能力/特点/经历不能成为最终边界，需覆盖新实体、时间节点、关系、世界机制等整个创作体系。通用模式 entry.py --world 已实现六种基本记录与可扩展实体类型/类别、多条提议、逐条证据判断、作者批量/选择确认，保留旧单条资料。时间与生效范围可记录，但尚非完整时间推理/日历系统；后续补时间线、状态变化、别名和编辑交互。正式 baseline 暂停，需扩展范围后再冻结提示和数据。
